# ADR-005: Authentication and identity propagation

- **Status:** Accepted
- **Amended:** 2026-10-03 (settled while building auth, #12, #25, PR #94, PR #120; see [Amendment](#amendment-2026-10-03-settled-while-building-auth-123)); 2026-10-20 (temporary reviewer patients, #357; see [Amendment](#amendment-2026-10-20-temporary-reviewer-patients-357))
- **Date:** 2026-09-28
- **Deciders:** Nick Delgado (+ Claude, drafting)
- **Related:** PRD FR-001…FR-003, FR-037, ADR-004, ADR-006, ADR-009

## Context

The patient logs in with a username and password on a simple login page. Every API call must be authenticated, and every tool call must be scoped to the logged-in patient. The browser also needs short-lived AWS credentials to stream audio to Transcribe (ADR-006).

## Options considered

1. **Cognito User Pool + custom login page.** Managed users, SRP password auth, JWTs verified by the API Gateway authorizer.
2. **Cognito managed login (hosted UI).** Less code, but the design is harder to control. The draft specifies our own page.
3. **Custom auth** (DynamoDB users + bcrypt + our own JWTs). More code and more risk, with no benefit.

## Decision

- A **Cognito User Pool**:
  - Self sign-up disabled; admins create the demo patients. *(Refined by the [2026-10-20 amendment](#amendment-2026-10-20-temporary-reviewer-patients-357): the request-access Lambda also creates temporary patients, as an admin call; self sign-up stays off.)*
  - The app client has no secret; auth flow `USER_SRP_AUTH`.
  - Strong password policy. MFA is off for the demo, and that is documented.
- A **custom React login page**, using the AWS Amplify Auth library (`signIn`/`signOut`/`fetchAuthSession`) with Cognito only. No Amplify backend.
- **API authorization:** an API Gateway REST API Cognito User Pool authorizer on every route. *(Except one: the [2026-10-20 amendment](#amendment-2026-10-20-temporary-reviewer-patients-357) adds a public route, `POST /api/request-access`, in envs that turn it on.)* The Lambda reads the patient ID from `requestContext.authorizer.claims.sub`.
- **Identity propagation to tools:** the chat handler builds `ToolContext { patientId: claims.sub, ... }` and passes it to the loop. **Tool schemas never include a patient ID** (CLAUDE.md, rule 1). *(Refined by the [2026-10-03 amendment](#amendment-2026-10-03-settled-while-building-auth-123): the handler binds `ToolContext` into the tool executor, and the loop never sees the patient ID.)*
- A **Cognito Identity Pool** exchanges the User Pool ID token for temporary AWS credentials. Its authenticated role allows only `transcribe:StartStreamTranscriptionWebSocket`. Unauthenticated identities are disabled.
- **Demo users** are created by `scripts/seed-users.ts` (`AdminCreateUser` + `AdminSetUserPassword --permanent`), which writes each fixture alias's Cognito `sub` to a git-ignored mapping (`.seed/cognito-users.<env>.json`). The data seed (#14) writes the matching `PATIENT#<sub>` profiles from that mapping; see the [2026-10-02 journal entry](../journal/2026-10-02-the-patient-id-is-a-sub-cognito-picks.md). Passwords come from a local, git-ignored `.env`. They are never in templates or the repo. *(Refined by the [2026-10-03 amendment](#amendment-2026-10-03-settled-while-building-auth-123): profiles moved to the data seed, PR #94.)* *(Refined by the [2026-10-20 amendment](#amendment-2026-10-20-temporary-reviewer-patients-357): the request-access Lambda creates temporary reviewer patients the same way.)*

## Consequences

- The authorizer rejects bad tokens before our code runs, so no auth code sits in the handlers.
- Using `sub` as the patient key ties the data to Cognito. That's acceptable for a proof-of-concept and is documented.
- Demo reviewers need credentials. The README says how to request them; they are not published in the repo. *(Refined by the [2026-10-20 amendment](#amendment-2026-10-20-temporary-reviewer-patients-357): a reviewer can also get a temporary account from the request page, where an env turns it on.)*
- **Revisit if** we need social login, MFA, or staff (non-patient) roles. That would mean Cognito groups plus role claims.

## Validation

- An API call without a token returns 401. An eval red-team scenario confirms the agent can't read another patient's data even when asked directly (ADR-008/009).

## Amendment (2026-10-03): settled while building auth (#123)

The decision stands. Building the auth stack (#12) and the login page (#25) settled these details:

- **Seeding is split** (PR #94): `seed-users.ts` creates the Cognito users and writes the alias → `sub` mapping; the data seed (#14) writes `PATIENT#<sub>` profiles. One writer per store. The Decision's "Demo users" line was edited in place on PR #94, before the amendment rule existed; this section records it.
- **Identity reaches the tools through the executor** (#15, #17): the chat handler binds `ToolContext` into the tool executor, and the loop never receives a patient ID (ADR-001's amendment).
- **App client** (#12): `ALLOW_USER_SRP_AUTH` + `ALLOW_REFRESH_TOKEN_AUTH`, `PreventUserExistenceErrors` on, token revocation on; ID and access tokens 60 min, refresh token 7 days (PRD FR-002).
- **Identity Pool** (#12, PR #94): enhanced flow only (`AllowClassicFlow: false`), `ServerSideTokenCheck: true`, so a signed-out or revoked user can't mint credentials.
- **The authorizer validates the Cognito ID token** (no OAuth scopes); the SPA sends it raw as `Authorization` (#17, #25).
- **SPA config is build-time** (PR #120): `VITE_USER_POOL_ID` and `VITE_SPA_CLIENT_ID`, read from SSM `/sched/<env>/auth/*` by the web deploy script (#100), which fails when either is missing. Voice adds a third, `VITE_IDENTITY_POOL_ID` from `/sched/<env>/auth/identity-pool-id`: #29 configures it in the SPA, and #100 passes it and fails without it, like the other two (decided on #123). Dev and tests fall back to an HTTP-level Cognito mock that does real SRP; production builds exclude it (#25).

## Amendment (2026-10-20): temporary reviewer patients (#357)

The decision stands for every patient the clinic has: the pool still has self sign-up off, and `AllowAdminCreateUserOnly` stays true because the new Lambda uses the admin calls. Owner decisions r1/Q-1, Q-3, Q-6 and A-3, A-5, A-14 on #357. This amendment covers the first of the issue's two PRs; the expiry job is the second.

- **A public route.** `POST /api/request-access` is the API's one method without `security: - CognitoUserPool: []`. It exists only where the `api` stack's `RequestAccess` parameter is `on` (in PR 1: the ephemeral check env; never `dev`, `demo` or `e2e`, which `scripts/deploy.sh` refuses). The stage throttle (rate 5, burst 10 per method) covers it. Its gates are the Turnstile check and two caps, not a token (ADR-009's amendment of the same date). The chat and session handlers don't change.
- **Temporary patients are created by a Lambda.** `AdminCreateUser` with no invitation message, then `AdminSetUserPassword` with `Permanent: true`, the two calls `scripts/seed-users.ts` makes, from one shared adapter (`@sched/api/cognito-admin`). The username is `user-` and 8 random lowercase letters or digits; the name and date of birth come from fixed lists of fictional values; the password is 16 random characters that meet the pool's policy. Nothing comes from the reviewer. The patient ID is the Cognito `sub`, so everything after sign-in is unchanged: the verified token, never the request, says whose data a call touches (CLAUDE.md rule 1).
- **A second writer of `PATIENT#<sub>` profiles.** The data seed (#14) writes the fixture patients' profiles; the request Lambda writes a temporary patient's, in the item shape `patientItem` gives (`@sched/tools/dynamo`), in one transaction with the registry entry's `sub`. A temporary patient starts with a profile only, no appointments, and counts as a new patient everywhere (r1/Q-5 (a)).
- **The IAM it needs.** The permissions boundary's `WorkloadServices` adds `cognito-idp:AdminCreateUser`, `AdminSetUserPassword`, `AdminGetUser`, `AdminDeleteUser`, `AdminUserGlobalSignOut` and `dynamodb:DeleteItem` (20 actions in all); the last two are for the expiry job and unused until it lands. The request function's role grants only `dynamodb:PutItem` and `UpdateItem` on the table and the four create-and-delete Cognito calls on this env's pool. `sched-cfn-exec` gains `EventsSchedRules`, the five rule actions on `sched-*` rules, for the job's SAM `Schedule` event. Nick applies the bootstrap stack.
- **The scheduling pattern.** The expiry job, in the second PR, is a SAM `Schedule` event on a function in the `api` stack: the pattern #325 can follow.
- **Still true:** no email, no name and no contact detail is collected; the sign-in page's test keeps its assertion that there is no sign-up link.
